# ADR-004: Large Monolithic Files Requiring Refactoring

- **Status**: Proposed
- **Date**: 2025-12-19
- **Owner**: Development Team
- **Stakeholders**: Frontend Engineering, Code Reviewers, Platform Engineering

## Context

The codebase has grown organically over time, resulting in several large monolithic files that are difficult to maintain, test, and understand. These files violate the Single Responsibility Principle and make it challenging for developers to quickly locate and modify specific functionality. Large files also increase the cognitive load required to work with the codebase and can lead to merge conflicts in team environments.

## Detailed Analysis and Recommendations

### 1. ProjectMessagesThread.tsx (1,272 lines)

**Current Issues:**
- Mixes file preview rendering, WebSocket message handling, UI layout, and attachment upload logic
- Contains numerous inline helper functions for file type detection
- Large component with excessive state management
- File preview logic embedded within the main component

**Recommended Breakdown:**
```
frontend/src/dashboard/features/messages/
├── ProjectMessagesThread.tsx (main component, ~300 lines)
├── components/
│   ├── FilePreview.tsx (file preview rendering logic)
│   ├── MessageInput.tsx (message input with attachments)
│   ├── MessageList.tsx (message display and scrolling)
│   └── EmojiPicker.tsx (emoji selection UI)
├── hooks/
│   ├── useMessageWebSocket.ts (WebSocket integration)
│   ├── useMessageState.ts (message state management)
│   └── useFileUpload.ts (file upload handling)
└── utils/
    ├── filePreviewHelpers.ts (file type detection and icons)
    └── messageFormatting.ts (message normalization)
```

**Benefits:**
- Easier to test individual components
- Better separation of concerns
- File preview logic can be reused elsewhere
- WebSocket logic isolated for easier debugging

## General Refactoring Principles

For all large files, follow these principles:

1. **Single Responsibility**: Each file should have one clear purpose
2. **Component Size**: Aim for components under 300 lines
3. **Hook Size**: Custom hooks should be under 200 lines
4. **Extract Utilities**: Move pure functions to utility files
5. **Separate Concerns**: Keep UI, business logic, and API calls in different files
6. **Type Safety**: Move type definitions to dedicated type files
7. **Constants**: Extract constants and configuration to separate files
8. **Reusability**: Create reusable components and hooks

## Implementation Strategy

### Phase 1: High Priority (api.ts, ProjectMessagesThread.tsx, QuickCreateTaskModal.tsx)
- Create new directory structures
- Extract types first (non-breaking)
- Move utility functions
- Split API clients by domain
- Extract sub-components
- Update imports incrementally

### Phase 2: Medium Priority (CreateLineItemModal.tsx, InvoicePreviewContent.tsx, HeaderStats.tsx, CalendarSurface.tsx)
- Apply same patterns as Phase 1
- Extract form components
- Separate calculation logic
- Create reusable UI components

### Phase 3: Lower Priority (Messages.tsx, useCalendarController.tsx, Collaborators.tsx)
- Refactor after patterns established
- Apply lessons learned from earlier phases
- Focus on hook composition

## Migration Guidelines

To minimize risk during refactoring:

1. **Keep Backward Compatibility**: Export from index files to maintain existing imports
2. **Test Coverage**: Add tests before refactoring
3. **Incremental Changes**: Refactor one file at a time
4. **Code Reviews**: Require reviews for all refactoring PRs
5. **Documentation**: Update component documentation
6. **Monitoring**: Watch for regressions after deployment

## Success Metrics

- Reduce average file size by 50%
- Improve test coverage for extracted modules
- Decrease merge conflict frequency
- Reduce time to locate specific functionality
- Improve developer onboarding time

## Follow-Up Actions

1. Create tracking issues for each file to be refactored
2. Establish refactoring guidelines document
3. Set up linting rules to prevent future large files (e.g., max-lines ESLint rule)
4. Schedule refactoring sprints for high-priority files
5. Create templates for common component patterns
